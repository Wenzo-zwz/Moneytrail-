# 本地生活、细分类与脱敏凭据

用户要求把餐饮和娱乐合并为“本地生活”，美团平台消费默认进入这个大类，并选择“长期保留脱敏凭据”。保留细类和消费平台用于以后回溯、统计；只有平台名时不猜具体订单。

## 行为

- 新大类：本地生活、购物、交通、居住、医疗、学习、其他、待分类。旧餐饮/娱乐数据继续可读，规范化为本地生活并保留餐饮/休闲娱乐细类，已有更具体细类不覆盖。
- 美团/三快等已知平台身份默认“本地生活”，细类为空显示“未细分”；京东/淘宝/天猫/拼多多默认购物，细类为空。明确药品、住宿、交通、教材等用途优先于平台默认。
- 使用现有关键词包含匹配和具体商户规则，保留个人规则、群收款、不明转账、退款、日期、格式与重复保护。禁止把共享平台身份记成永久具体用途。
- 细类未知不阻止正常消费入账，也不要求逐笔确认。月统计可展开大类，包含未细分，细类净额与大类合计一致。
- 保留每笔商户描述和独立平台字段。以后入账前保存脱敏短信凭据：隐藏银行卡尾号与余额，保留交易描述、金额、时间、银行签名和当时分类依据；原文不再是唯一回溯来源。
- 待确认原文暂存行为维持；入账后仍清原文，但账本内脱敏凭据长期保留，不受收件箱30天处理元数据清理影响。忽略不新增账目或凭据。不操作手机原短信。
- JSON/CSV备份与导入保留新增字段。旧备份兼容。正常编辑、分类批处理和退款关联必须保留脱敏凭据；关联退款继承原消费分类/细类/平台。
- 不伪造历史原文。已清除原文的历史只能用现存商户描述补类别/细类/平台，不把重新拼接文字标成原始凭据。今后短信仍只有“三快”时，细类继续未知，订单详情需支付账单或订单补充。

## 字段契约

保持账本 `version: 1`，为 Transaction/DraftTransaction 增加可选字段：

```ts
subcategory?: string; // 非空，最多40字；缺失表示未细分
platform?: "美团" | "京东" | "淘宝" | "天猫" | "拼多多" | "滴滴";
smsEvidence?: {
  text: string; // 脱敏内容，1..3000字
  receivedAt?: string; // ISO时间，缺失用于手动粘贴
  classificationReason?: string; // 最多200字
  ruleVersion?: string; // 最多64字
};
```

旧餐饮规范化时默认 subcategory=餐饮，旧娱乐默认 subcategory=休闲娱乐。UI大类只显示新列表，但旧类别作为读取/导入输入继续接受。服务端接受新旧类别，分类函数输出新类别；历史迁移另行执行。旧客户端保存同一交易时遗漏新增元数据，数据库必须保留原有 subcategory/platform/smsEvidence，避免静默丢失；显式更改细类支持新值（新UI删除细类可用删除后特定兼容策略或清晰的未知选项，不能意外由旧客户端清空）。

细类建议：本地生活＝餐饮、外卖、堂食、咖啡奶茶、休闲娱乐、按摩足疗、剧本杀密室、电影影音、桌游台球、景区游玩；购物＝烟酒副食、超市便利、服饰、数码、日用品；其他大类按明确用途可有细类，未知保持缺失。没有依据时不推测细类。

## 验证和上线

- 先测模型兼容、细类统计、导入导出、脱敏边界，再实现；TS/SQL共享分类案例一致。
- 真实本地数据库测试覆盖全部自动/手动确认/批量/重新识别路径；每条成功入账的未来短信都保存脱敏凭据；余额和尾号不得出现在新凭据。
- 数据库函数保持权限、账户隔离、锁序和CAS；迁移DDL不隐式改账。
- 旧客户端不能清空已有新字段。历史只作用于已验证所有者和明确选中账目，保留金额/日期/交易编号/备注/退款关联，不处理不明转账。
- 完成独立审查、测试、真实项目迁移、历史修正与网页发布验证。
